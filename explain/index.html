Project guide คู่มือโปรเจกต์

BinaryBearx ESP Web Flasher

This project is a static browser-based ESP firmware flasher. It uses HTML, JSON, and firmware manifest files — not a backend API — to show firmware options and flash ESP32 / ESP8266 devices directly from the browser.

โปรเจกต์นี้เป็นหน้าเว็บแฟลชเฟิร์มแวร์แบบ static ทำงานในเบราว์เซอร์ ใช้ HTML, JSON และ manifest ของเฟิร์มแวร์ โดยไม่ต้องมี backend API เพื่อแสดงรายการเฟิร์มแวร์และแฟลชไปยัง ESP32 / ESP8266 โดยตรงจากเบราว์เซอร์

How the project works การทำงานของโปรเจกต์

UI flow mapping when a user selects firmware

แผนภาพการไหลของ UI เมื่อผู้ใช้เลือกเฟิร์มแวร์

A clear UI should expose the flashing path as a visible sequence: what was loaded, what was selected, when the browser asks for a device, and where success or failure can happen.

01 Loading Page loads firmware data

The page fetches index.json from the public firmware host and prepares the dropdown.

02 Check Browser capability is checked

If Web Serial is unavailable, the UI must stop here and explain why flashing cannot continue.

03 Ready Firmware list is ready

The firmware choices are visible, but install should still wait until the user selects one item.

↓
04 Select User chooses a firmware

The selected manifest name is resolved into a full manifest URL and bound to the install button.

05 Install User clicks install

The browser starts the ESP Web Tools flow for the selected manifest.

06 Connect User selects a serial port

The browser asks which connected ESP device should be used for flashing.

↓
07 Flashing Tool downloads and writes binaries

The manifest is read, binaries are downloaded from the configured host, and data is written to the ESP device.

↓
08 Success Flashing completed

The UI should show the selected firmware name, completion status, and a simple next action.

08 Error Flashing failed

The UI should distinguish manifest issues, download failures, serial access problems, and unsupported browsers.

JSON roles หน้าที่ของ JSON

What index.json is made for

index.json มีไว้ทำอะไร

firmware/index.json is the list used by the UI. In the current project, this file is served from the public GitHub Pages repository. It does not contain flashing details. Its only job is to tell the page which manifest entries are available and what label to show for each one.

  • Acts as the source for the dropdown menu.
  • Keeps the main page simple, because firmware options can change without editing much JavaScript.
  • Lets the public repository own firmware metadata while the website can live on a separate domain.
  • Lets you add, remove, or rename firmware options in one place.

Example `index.json`

[
  {
    "name": "AIS 4G Board [VirtualThing for test]",
    "file": "manifest-virtualthingconn.json"
  },
  {
    "name": "ADI Example 3 Sensors",
    "file": "manifest-ADI-3sens.json"
  }
]

firmware/index.json คือรายการที่ UI ใช้อ่านเพื่อสร้างเมนูเลือกเฟิร์มแวร์ โดยในโปรเจกต์ปัจจุบันไฟล์นี้ถูกเสิร์ฟจาก public GitHub Pages repository ไฟล์นี้ไม่ได้เก็บรายละเอียดการแฟลช หน้าที่ของมันคือบอกว่ามี manifest อะไรบ้าง และแต่ละอันควรแสดงชื่ออะไร

  • เป็นแหล่งข้อมูลของ dropdown
  • ทำให้หน้าหลักเรียบง่าย เพราะเพิ่มหรือลดเฟิร์มแวร์ได้โดยแทบไม่ต้องแก้ JavaScript
  • ช่วยให้ public repository เป็นเจ้าของ metadata ของเฟิร์มแวร์ได้ แม้หน้าเว็บจะอยู่คนละโดเมน
  • ช่วยให้จัดการการเพิ่ม ลบ หรือเปลี่ยนชื่อรายการได้จากจุดเดียว

JSON roles หน้าที่ของ JSON

What manifest JSON is made for

manifest JSON มีไว้ทำอะไร

A manifest file contains the flashing instructions for one firmware package. This is the file ESP Web Tools reads when the user clicks install.

  • Defines which chip or board the package targets.
  • Lists binary files and the flash addresses used during install.
  • Can include metadata such as name, version, and optional behavior like Improv support.

Example manifest JSON

{
  "name": "AIS 4G Board [VirtualThing for test]",
  "version": "1.0.0",
  "new_install_prompt_erase": true,
  "builds": [
    {
      "chipFamily": "ESP32",
      "parts": [
        {
          "path": "https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/virtualThingConn/bootloader.bin",
          "offset": 4096
        },
        {
          "path": "https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/virtualThingConn/partitions.bin",
          "offset": 32768
        },
        {
          "path": "https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/virtualThingConn/firmware.bin",
          "offset": 65536
        }
      ]
    }
  ]
}

ไฟล์ manifest คือคำอธิบายชุดคำสั่งสำหรับแฟลชเฟิร์มแวร์หนึ่งชุด เป็นไฟล์ที่ ESP Web Tools จะอ่านตอนผู้ใช้กดติดตั้ง

  • กำหนดว่าเฟิร์มแวร์นี้ใช้กับชิปหรือบอร์ดประเภทใด
  • ระบุไฟล์ไบนารีและ address ที่ต้องใช้ตอนแฟลช
  • อาจมีข้อมูลเพิ่มเติม เช่น ชื่อ เวอร์ชัน และพฤติกรรมเสริมอย่าง Improv

What to prepare สิ่งที่ต้องเตรียม

Checklist for adding or updating firmware

สิ่งที่ต้องเตรียมเมื่อเพิ่มหรือแก้เฟิร์มแวร์

  1. Create or update the manifest file in firmware/.
  2. Add the manifest entry to firmware/index.json.
  3. Make sure every binary URL in the manifest is valid and accessible.
  4. Make sure the frontend knows the public GitHub Pages base URL used to resolve file entries into full manifest URLs.
  5. Keep the display name short and understandable for users.
  6. Open index.html in Chrome or another Chromium-based browser to confirm the list loads and the install button reacts to selection.
  1. สร้างหรือแก้ไฟล์ manifest ใน firmware/
  2. เพิ่มรายการ manifest ลงใน firmware/index.json
  3. ตรวจว่า binary URL ทุกตัวใน manifest เปิดได้จริง
  4. ตรวจว่า frontend รู้จัก base URL ของ public GitHub Pages ที่ใช้ประกอบค่า file ให้กลายเป็น full manifest URL
  5. ตั้งชื่อที่แสดงให้สั้นและเข้าใจง่ายสำหรับผู้ใช้
  6. เปิด index.html ใน Chrome หรือเบราว์เซอร์ตระกูล Chromium เพื่อตรวจว่ารายการโหลดขึ้นและปุ่มติดตั้งเปลี่ยนตามที่เลือก

Deployment study cases กรณีศึกษาการ deploy

If you deploy it another way

ถ้านำไป deploy แบบอื่นควรศึกษาอะไร

Study the hosting path rules first. The current project uses a custom-domain web app, while images, index.json, manifest files, and binaries are served from a public GitHub Pages repository.

UI topology for split hosting

Web app host Your static host

Hosts index.html, UI logic, styles, and the install button on your own domain such as https://flash.example.com.

Browser User opens the flasher UI

The browser loads the page from your host, runs the frontend logic, and starts the firmware lookup flow.

Firmware catalog GitHub Pages serves index.json

The UI fetches the firmware list from GitHub Pages so you can update choices without redeploying the web app.

↓
Manifest Selected entry becomes manifest URL

The selected file value is resolved to a full GitHub Pages manifest path such as /firmware/manifest-v1.json.

Binary source GitHub Pages serves firmware binaries

The manifest points to bootloader.bin, partitions.bin, and firmware.bin files hosted in the same public repository.

Flashing ESP Web Tools writes to the device

After the user approves serial access, the browser downloads the binaries and flashes the connected ESP board.

  • GitHub Pages subpath: public files are under paths like https://binarybearzz.github.io/BinaryBearx-esp-web-tool/....
  • Custom-domain web app: the website itself can live elsewhere, but must fetch the firmware metadata from the public repository.
  • Local file open: opening with file:// is a bad test for this app because fetch("firmware/index.json") may fail. Use a simple local server.
  • Static host/CDN: confirm the manifest and binary files are publicly readable over HTTPS.

Current study case: custom domain for the web, public GitHub Pages for firmware files.

Web app:
https://flash.example.com/

Firmware files:
https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/index.json
https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/manifest-v1.json
https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/version1/app.bin

In this case, your web page on flash.example.com should not fetch firmware/index.json as a local relative path anymore, because that would look for https://flash.example.com/firmware/index.json. Instead, the page must fetch the full GitHub Pages URL and resolve manifest names against that same public base.

  • The firmware list source becomes a full URL, for example https://binarybearzz.github.io/BinaryBearx-esp-web-tool/firmware/index.json.
  • If index.json still contains only filenames like manifest-v1.json, the frontend must prepend the GitHub Pages firmware base path before passing it to the install button.
  • If manifests already use full GitHub Pages binary URLs, they are independent from the custom-domain website path.
  • If manifests reference absolute external URLs, those URLs must remain public and stable.

สิ่งแรกที่ควรศึกษาคือกฎเรื่อง path ของระบบโฮสต์ โดยโปรเจกต์ปัจจุบันใช้หน้าเว็บบน custom domain แต่รูปภาพ, index.json, manifest และ binary ถูกเสิร์ฟจาก public GitHub Pages repository

Hosting, CDN, and limits Hosting, CDN และข้อจำกัด

What this page needs, what CDN helps with, and current constraints

สิ่งที่หน้าเว็บนี้ต้องใช้ บทบาทของ CDN และข้อจำกัดปัจจุบัน

This page does not require a backend or a CDN by itself. It only needs public static hosting for the page, the firmware catalog, manifest files, and binary files. A CDN becomes useful when you want faster global downloads, better cache control, or a more stable delivery path for large binaries.

  • Required hosting: the web page, index.json, manifests, and binaries must be reachable over HTTPS.
  • CORS: the host serving manifests and binaries must allow browser access, or downloads may fail.
  • CDN is optional: use it if binaries are large, users are in many regions, or GitHub Pages is not the final delivery channel.
  • Stable URLs: if manifest or binary URLs change, expire, or become private, flashing breaks immediately.
  • Cache/versioning: versioned filenames or cache-busting help prevent users from flashing stale binaries.
  • Trust and integrity: binary hosts should be controlled by you or a trusted release pipeline.
  • Not supported over file://: opening the page directly from the filesystem is not a reliable test because fetch() may fail.
  • Browser limitation: flashing depends on Web Serial, so Safari and Firefox are not valid targets for the install flow.
  • User permission limitation: the page cannot auto-select a serial port or bypass the browser permission dialog.

หน้าเว็บนี้ไม่ได้บังคับว่าต้องมี backend หรือ CDN เสมอไป สิ่งที่ต้องมีจริง ๆ คือ static hosting ที่เปิดสาธารณะสำหรับหน้าเว็บ รายการเฟิร์มแวร์ manifest และไฟล์ binary ส่วน CDN จะมีประโยชน์เมื่ออยากให้ดาวน์โหลดได้เร็วขึ้นจากหลายภูมิภาค คุม cache ได้ดีขึ้น หรือมีเส้นทางส่งไฟล์ที่เสถียรกว่าสำหรับ binary ขนาดใหญ่

  • สิ่งที่ต้องมี: หน้าเว็บ, index.json, manifest และ binary ต้องเปิดผ่าน HTTPS ได้จริง
  • CORS: host ที่เสิร์ฟ manifest และ binary ต้องอนุญาตให้เบราว์เซอร์เข้าถึง ไม่เช่นนั้นการดาวน์โหลดจะล้มเหลว
  • CDN เป็นตัวเลือก: ควรใช้เมื่อไฟล์ binary ใหญ่ ผู้ใช้อยู่หลายภูมิภาค หรือ GitHub Pages ไม่ใช่ช่องทางส่งไฟล์สุดท้าย
  • URL ต้องเสถียร: ถ้า URL ของ manifest หรือ binary เปลี่ยน หมดอายุ หรือกลายเป็น private การแฟลชจะพังทันที
  • Cache/versioning: ควรมีชื่อไฟล์แบบมีเวอร์ชันหรือ cache-busting เพื่อไม่ให้ผู้ใช้แฟลชไฟล์เก่า
  • ความน่าเชื่อถือ: host ของ binary ควรถูกควบคุมโดยคุณหรือ release pipeline ที่เชื่อถือได้
  • ไม่เหมาะกับ file://: การเปิดไฟล์ตรงจากเครื่องไม่ใช่วิธีทดสอบที่เชื่อถือได้ เพราะ fetch() อาจล้มเหลว
  • ข้อจำกัดของเบราว์เซอร์: การแฟลชพึ่งพา Web Serial ดังนั้น Safari และ Firefox ใช้ flow ติดตั้งนี้ไม่ได้
  • ข้อจำกัดด้านสิทธิ์: หน้าเว็บไม่สามารถเลือก serial port แทนผู้ใช้หรือข้ามหน้าต่างขอสิทธิ์ของเบราว์เซอร์ได้

Why Chrome / Chromium matters

ทำไมต้องใช้ Chrome / Chromium

The flashing flow depends on the Web Serial API. That API is supported in Chromium-based browsers, so the page shows a warning if the browser does not support it.

กระบวนการแฟลชพึ่งพา Web Serial API ซึ่งรองรับในเบราว์เซอร์ตระกูล Chromium ดังนั้นหน้าเว็บจะแจ้งเตือนถ้าเบราว์เซอร์ไม่รองรับ

How to think about the project

มองโปรเจกต์นี้แบบไหนจะเข้าใจง่าย

The page is a menu + launcher. The HTML builds the UI, the JSON file supplies the available firmware choices, and each manifest tells ESP Web Tools what to flash.

หน้านี้คือ เมนู + ตัวสั่งงาน โดย HTML สร้าง UI, ไฟล์ JSON จัดเตรียมตัวเลือกเฟิร์มแวร์ และ manifest จะบอก ESP Web Tools ว่าต้องแฟลชอะไร

Keep manifest labels user-facing and descriptive, because they appear directly in the dropdown. ควรตั้งชื่อ manifest ให้คนอ่านเข้าใจง่าย เพราะชื่อเหล่านี้จะแสดงตรงใน dropdown

If the project grows, separate explanation pages can be added for firmware conventions, browser support, or manifest format.

ถ้าโปรเจกต์ใหญ่ขึ้น สามารถแยกหน้าคำอธิบายสำหรับ convention ของเฟิร์มแวร์ การรองรับเบราว์เซอร์ หรือรูปแบบ manifest ได้
